# pdfcraft-platform

Layer L7 holds operating-system services that both the desktop app (`pdfcraft-ui-egui`) and the automation tools (`pdfcraft-automation`) need. Those two crates sit on the same layer and can't depend on each other, so a helper they share lives here instead of being copied into each (`xtask/src/layers.rs` allows both edges). It has no UI dependencies; macOS filesystem calls use the safe `rustix` wrapper, and only the `https` feature brings in a network stack.

`staging` creates the temporary file an atomic save writes before renaming it over the target. The file is opened with `create_new`, so anything already at the name (a file, a hard link, a symbolic link even when dangling, a folder) is skipped and never written through. On Windows a folder at the name fails with "access denied" rather than "already exists", and is skipped only when something is actually there. Names carry an unpredictable 64-bit suffix from `staging_suffixes` (the standard library's keyed hash, currently SipHash-1-3, keyed from the operating system's random source), which stops a name being planted in advance but is not a CSPRNG; fixed suffixes are only for tests. At most 16 names are tried, and then the save is refused. The target's name is cut to 128 bytes on a character boundary so the staging name fits every system's limit. Each caller keeps its own name form (`.{name}.{suffix}.pdfcraft-tmp` for automation, `.{name}.pdfcraft-{suffix}.tmp` for the desktop save). Writing, closing the file before the rename, renaming and removing the staging file on failure stay with the caller.

Synthetic tests pin both name forms, the 128-byte cut, the attempt limit and refusal when no name is left. The planted-file, link, folder and failed-rename tests stay with each caller, where they exercise the whole save.

On macOS, `write_atomically_with` copies the existing regular destination's accessible extended attributes to the open staging file after writing the data and before flushing and renaming. Finder tags, comments, binary values and empty attributes therefore survive both incremental and full saves (#2658). Save As retains attributes of an existing destination; a new destination does not inherit metadata from the source PDF. Missing files and filesystems without xattr support keep working. The metadata read does not follow the destination's symlink or block on a FIFO. macOS manages the new file's `com.apple.provenance`; it is not copied. Kernel-hidden compression attributes are not requested.

Attribute copying is bounded: 64 KiB of names, 1024 attributes, 16 MiB per value and 64 MiB total. Each value must fill the initially queried size and retain that size in a second query after reading: a resource fork may return a partial prefix on growth rather than an error. A read/copy error or exceeded bound returns an error suggesting Save As; the original bytes and metadata stay intact and the staging file is removed. Flush errors retain the same guarantee. Tests cover exact metadata before flush and after repeated saves, empty/binary values, oversized resource forks, a simulated partial read of a growing fork and symlink isolation. Automation covers incremental/full saves, Save As and retaining an unsaved edit after metadata refusal. The staging writer also retains Unix permissions and, where supported, Windows/macOS creation dates; attribute copying runs before the creation date is restored. ACLs and hard-link identity are not preserved.

`https` (cargo feature `https`, turned on only by the desktop app and `pdfcraft-cli`) is the network remote signing goes through: `pdfcraft-sign` builds every request and never opens a socket, and `https::transport()` carries them. It speaks HTTPS through ureq and rustls, checked against the certificate authorities the operating system trusts (loaded at the first request, not when the transport is made; no bundled root list), and plain HTTP only to this computer, which is what `remote::check_url` allows. Every address is checked again before connecting. Redirects are never followed: a 3xx answer is an error, since it leads to an address nobody checked and neither protocol uses one. A 4xx or 5xx answer is returned as it is, because the protocols put their errors in its body. A body is read to at most `remote::MAX_RESPONSE` plus one byte, which is how the signing code tells an answer too large from one that fits. Connecting, with the TLS handshake, may take 15 seconds, and one exchange 150: a CSC service may hold an authorization open until the user confirms the signature on a phone, instead of answering at once and being asked again. A proxy set in the environment (`HTTPS_PROXY`, `ALL_PROXY`) is used for HTTPS but never for plain HTTP, which would otherwise carry the password across the network. Failures are described in words of our own, never by quoting the request, whose headers hold the password or an access token.

Logging: ureq and ureq-proto log at `trace` every request and answer as it crosses the wire, before TLS and unredacted, so the Authorization header (a CSC service's Basic user name and password, or its access token) and the tokens in the answers would reach the log. A logger in a program that uses this transport must cap the targets `ureq`, `ureq_proto` and `rustls`, and their modules, at `debug` whatever `RUST_LOG` asks for, as the desktop app's does (`WIRE_TARGETS` in `apps/pdfcraft/src/logging.rs`). `pdfcraft-cli` installs no logger, so nothing of theirs is written there.

The crate has itself as a dev-dependency with `https` on, so `cargo test -p pdfcraft-platform` and `cargo clippy -p pdfcraft-platform --all-targets` cover the transport and its tests (the wasm check builds no dev-dependency). `tests/https.rs` runs a plain HTTP/1.1 server on 127.0.0.1 in front of the in-process signing service (`remote::mock`) and lists, sends the OTP and signs over real sockets for CSC and ARSS, and checks that redirects aren't followed, answers stop at the cap with or without a length, a closed port reads as unreachable and an environment proxy is skipped for loopback. The unit tests in `src/https.rs` serve HTTPS on 127.0.0.1 with a self-signed certificate (rustls's server side, already in the graph through ureq): trusted, a CSC service lists and signs through it; trusted by neither another authority nor the system, the handshake fails with rustls's certificate reason before the server reads a byte of the request (and its Basic password); with no authority at all, nothing connects; and a handshake that never comes times out at the connect limit, not the exchange's.
